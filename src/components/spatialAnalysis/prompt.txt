# Build a Client-Side Spatial Query Feature in My Existing Web GIS

I have an existing **Web GIS application** built with:

* **React.js**
* **JavaScript** — not TypeScript
* **Ant Design** for UI components
* **Leaflet.js** for map rendering and interaction
* **Turf.js** for spatial/geometric operations
* **Flatbush** for spatial indexing
* An existing **chunking hook** for processing large datasets incrementally

I want to implement a complete, production-oriented **Spatial Query module** inside my existing Web GIS.

The most important requirement is that the Spatial Query system must support **flexible source and target selections**.

---

# IMPORTANT CONSTRAINTS

1. Do **NOT** introduce Web Workers.
2. All spatial processing must happen on the client side.
3. Reuse the project's existing chunking hook.
4. Reuse the project's existing Flatbush spatial indexes wherever possible.
5. Before implementing anything, inspect the existing project architecture.
6. Reuse existing map, layer, feature-selection, drawing, highlighting, popup, indexing, and state-management functionality.
7. Do not replace Leaflet.
8. Do not replace Ant Design.
9. Do not introduce TypeScript.
10. Do not introduce another spatial indexing library.
11. Do not modify unrelated features.
12. Follow the existing project's coding conventions.
13. Do not create duplicate utilities when equivalent functionality already exists.
14. Use the existing installed versions of React, Leaflet, Turf.js, Flatbush, and Ant Design.
15. Keep the implementation modular and extensible.
16. All spatial calculations must be performed client-side.

---

# 1. CORE SPATIAL QUERY MODEL

The query must NOT be designed around only:

```text
Source Layer → Target Geometry
```

Instead, both **Source** and **Target** must support different selection scopes.

The conceptual query is:

```text
SOURCE
   │
   │ spatial relationship
   ▼
TARGET
```

Where SOURCE can represent:

* A complete layer
* A single feature from a layer
* Multiple features from a single layer

Where both SOURCE and TARGET can represent:

* A complete layer
* Multiple layers
* A single feature from a layer
* Multiple features from a single layer
* Multiple features across multiple layers

# 6. IMPORTANT MULTI-TARGET SEMANTICS

When multiple target layers/features are selected, define the query behavior clearly.

For relationship operations such as:

```text
Within
Contains
Intersects
Overlaps
Touches
Crosses
Disjoint
```

the default behavior should be:

> A source feature is considered a match if it satisfies the selected spatial relationship with **at least one target feature**.

Example:

```text
Source:
Building #101

Targets:
Flood Zone #1
Flood Zone #2
Flood Zone #3
```

If:

```text
Building #101 INTERSECTS Flood Zone #2
```

then:

```text
Building #101 = MATCH
```

even if it does not intersect Zone #1 or Zone #3.

Conceptually:

```javascript
sourceFeature
    ↓
compare against targetFeatures
    ↓
target #1 → false
target #2 → true
target #3 → false
    ↓
MATCH
```

Avoid returning the same source feature multiple times if it matches multiple targets.

# 7. PRESERVE MATCH INFORMATION

Although duplicate source features should not appear in the final result table, the query engine should preserve information about what caused the match.

For example:

```javascript
{
  source: {
    layerId: "buildings",
    featureId: "building-101",
    feature: ...
  },

  matchedTargets: [
    {
      layerId: "flood-zones",
      featureId: "zone-2",
      feature: ...
    },
    {
      layerId: "flood-zones",
      featureId: "zone-3",
      feature: ...
    }
  ]
}
```

This will allow the UI to later display:

```text
Building #101
Matched:
  Flood Zone #2
  Flood Zone #3
```

Do not discard this relationship information.

# 8. SOURCE/TARGET NORMALIZATION

Create a normalization layer before spatial processing.

The UI can have complex selections, but the query engine should receive a predictable structure.

For example:

```javascript
{
  source: {
    type: "features",
    items: [
      {
        layerId: "buildings",
        featureId: "building-101",
        feature: ...
      },
      {
        layerId: "buildings",
        featureId: "building-102",
        feature: ...
      }
    ]
  },

  target: {
    type: "features",
    items: [
      {
        layerId: "flood-zones",
        featureId: "zone-1",
        feature: ...
      },
      {
        layerId: "rivers",
        featureId: "river-4",
        feature: ...
      }
    ]
  },

  operation: "intersects"
}
```

The query engine should operate on this normalized representation.

This prevents the core spatial algorithms from becoming tightly coupled to the UI.

# 14. SPATIAL OPERATION COMPATIBILITY

The UI must dynamically determine which source/target combinations are valid for each operation.

Do not simply expose every operation for every geometry combination.

For example:

```text
Point
  ↓
Within
  ↓
Polygon
```

is valid.

But some Turf operations have geometry-specific requirements.

The system should:

1. Determine source geometry types.
2. Determine target geometry types.
3. Determine operation compatibility.
4. Disable or hide incompatible operations.
5. Provide a clear explanation when necessary.

Example:

```text
⚠ This spatial operation is not supported
for the selected geometry types.
```

# 15. FLATBUSH WITH MULTIPLE LAYERS

Flatbush must be used intelligently with multi-layer targets.

Do not assume there is only one index.

The existing project may have:

```text
Layer A → Flatbush Index A
Layer B → Flatbush Index B
Layer C → Flatbush Index C
```

The query engine should reuse these indexes.

For:

```text
Target:
Flood Zones + Rivers + Roads
```

perform candidate searches against the relevant indexes rather than scanning every feature.

Conceptually:

```text
                 QUERY GEOMETRY
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
      Flood Index   River Index   Road Index
          │            │            │
          ▼            ▼            ▼
      Candidates    Candidates    Candidates
          │            │            │
          └────────────┼────────────┘
                       ▼
                Exact Turf Tests
                       │
                       ▼
                 Query Results
```

# 24. PERFORMANCE REQUIREMENTS

For large datasets:

### DO

* Use existing Flatbush indexes.
* Use the existing chunking hook.
* Normalize selections without copying large geometries unnecessarily.
* Filter attributes before spatial calculations where possible.
* Use bounding-box candidate filtering.
* Run exact Turf operations only on candidates.
* Deduplicate source results.
* Preserve only required metadata.
* Avoid unnecessary React state updates.

### DON'T

* Compare every source feature against every target feature when avoidable.
* Rebuild Flatbush unnecessarily.
* Clone entire GeoJSON collections.
* Put huge feature collections into React state.
* Trigger a React render for every processed feature.
* Introduce Web Workers.
* Introduce another spatial-index library.
